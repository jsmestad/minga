Runtime & Process Design

Architecture & Buffer-Aware Agents

How Minga splits state ownership inside one BEAM VM from native rendering and parsing across explicit OS process boundaries, and how agents edit in-memory buffer forks instead of writing blind to disk.

1. BEAM core + native ports 2. Buffer-aware staged edits 3. Ownership & recovery 4. Architecture decisions

1. One BEAM core, thin native OS processes

Minga does not ask one runtime to do everything. All editing state, concurrency, supervision, agent orchestration, and semantic UI modeling live inside an Elixir/OTP 29 BEAM process. Rendering, native accessibility, immediate gesture response, and tree-sitter parsing run in separate native OS processes over binary stdin/stdout ports with zero shared memory.

2. How buffer-aware agent edits work

Standalone CLI harnesses read and overwrite files directly on disk, which breaks open-buffer undo and forces separate Git worktrees the moment two tasks overlap. In Minga, every buffer is a BEAM process and agent file tools have no blind filesystem write fallback.

3. Why these boundaries hold under load

  • One interactive mailbox, explicit value owners. MingaEditor stays a single GenServer so keystrokes, shell changes, and renderer receipts remain strictly ordered, while 16 immutable value modules own their own transitions (enforced by custom Credo checks with an empty allowlist). New processes are created for independent failure or lifecycle boundaries, not per UI widget.
  • Lossless continuation and honest crash recovery. MingaAgent.Session stores the exact provider continuation beside the display transcript and records single-attempt tool admission before executing external effects. If a process dies mid-tool, recovery marks the call indeterminate and never silently replays a side effect (Session Recovery).
  • Coalescing stream ingest. Rapid model token deltas pass through MingaEditor.Agent.Ingest with leading-and-trailing-edge batching so streaming at hundreds of chunks per second cannot create head-of-line latency ahead of your keystrokes.

4. Five architecture decision records

Minga records major structural decisions as concise ADRs so contributors and extensions share the same invariants:

  • ADR-0001 Frontends own row fit. Swift and Go measure how many rows fit their pixel or terminal area once and report that count; the BEAM never derives row counts from pixel math or line spacing.
  • ADR-0002 Editor state transitions have explicit owners. One writer per struct, one MingaEditor mailbox, and typed asynchronous effects through MingaEditor.EffectScheduler.
  • ADR-0003 Extension code updates require a new VM generation. Config reload (SPC h r) applies options, bindings, hooks, and advice in place; compiled extension packages activate cleanly on restart rather than mixing module versions.
  • ADR-0004 Programmable workbench over fixed engine authorities. The v0.1.0 direction: author readable Elixir over fixed buffer, agent, and permission owners; Save to activate; Keep useful definitions across projects.
  • ADR-0005 Frontends own immediate UI feedback. Frontends handle smooth gesture and scroll motion locally over resident committed models while semantic edits and cursor decisions remain authoritative in the BEAM.
