Runtime & Process Design

Architecture & Staged Agent Edits

Why Minga splits concurrent state management inside the Erlang virtual machine (BEAM) from native rendering and syntax parsing across separate OS processes, and how staged overlays protect open buffers from blind disk writes.

1. Core & native processes 2. Staged agent edits 3. Runtime guarantees & tradeoffs 4. Key design decisions

1. One concurrent core, thin native OS processes

Minga uses four languages deliberately, each behind a strict OS process boundary so nothing shares memory across them. Elixir on the Erlang VM owns everything concurrent and stateful (open files, agent sessions, language servers, extensions). Swift, Go, and Zig stay intentionally thin: Swift draws macOS, Go draws the terminal, and Zig parses C tree-sitter grammars.

2. How staged agent edits protect your open files

Agent file tools in Minga have no blind filesystem write fallback. Approved edits land in an isolated staging overlay while your open buffers and working tree remain untouched until you explicitly publish or discard them.

3. Real runtime guarantees and real tradeoffs

  • One ordered interactive mailbox, isolated background work. Editor input stays serialized in one process so keystrokes, view switches, and render frames remain strictly ordered, while open buffers, language servers, save hooks, extensions, and agent sessions each run in separate preemptively scheduled processes with separate heaps. Fast model streams are batched ahead of the editor mailbox so token deltas do not queue ahead of typing.
  • Current staging tradeoffs (worth knowing). Because staged edits stay off your working tree until you publish, language servers inspect the published open buffer rather than unpublished forks, and the diff review pane is a read-only viewer (switch to the buffer to hand-edit). When an agent runs shell commands such as tests, Minga materializes the staged overlay into a temporary directory with an isolated build path so your main build stays untouched; projects relying on untracked node_modules or .git inside shell tests should keep that boundary in mind.
  • Crash-safe tool recording. Each agent session saves the exact provider conversation beside the visible transcript and writes a single-attempt admission record before dispatching external tool effects. If a process dies mid-tool, recovery marks that call indeterminate and never silently replays a side effect (Session Recovery Reference).

4. Key architectural decisions

Minga documents five structural invariants as Architecture Decision Records in the repository:

  • ADR-0001 Clients measure their own viewport rows. Swift and Go calculate how many rows fit their pixel or terminal area once and report that count; the core never guesses rows from pixel math or line spacing.
  • ADR-0002 Explicit state owners. Each sub-state has one owning module that performs its updates, while interactive commands stay serialized in one editor mailbox.
  • ADR-0003 Extension code updates activate on restart. Config reloads apply options, bindings, hooks, and advice in place; compiled extension packages activate cleanly on restart rather than mixing old and new module code mid-session.
  • ADR-0004 Programmable workflows over fixed engine owners (v0.1.0 roadmap). Author readable workflows over existing buffer, agent, and permission boundaries; save to activate; discard when one-off or keep useful definitions across projects.
  • ADR-0005 Clients own immediate visual motion. Native clients handle smooth trackpad scrolling and local previews over committed layout data while text edits and cursor position remain authoritative in the core.
