ARCHITECTURE Why it is safe

A slow language server does not freeze your typing. An approved edit waits for you.

You are about to let an agent work in your repository, so two things have to hold. A slow language server or a busy agent does not freeze your typing. And in a project you open in the editor, an edit you approve is staged: the file on disk and your open buffer keep the old text until you publish.

Neither promise is unlimited. An extension command that hangs does block your keys, and a shell command or a Git commit the agent runs is not a staged edit. This page shows both promises working, then lists where they stop.

If the language server takes 3 seconds to answer

  1. The language server has not answered. On the left, your keys wait in a queue behind the request. On the right, Minga draws each key as it arrives, because the request went to another process.
  2. The answer came back. The left editor drew the waiting keys in one jump. Minga had already drawn each one.

If the parser crashes

  1. The parser crashed. The left editor ran it in the same process, so the editor is gone. Minga runs the parser as a separate program: only the parser stopped, and you keep typing.
  2. Minga started a new parser and gave it the buffer to read again. Your text and its highlighting stayed where they were the whole time. The left editor has to be reopened.

Minga does not run that work on the loop that handles your keys. One process takes your keys in order. The language server client, each agent session and the parser are separate processes, so a request to one of them is a message, and your next key does not wait for the server's answer. When a language server, an agent session, an extension or that key-handling process itself crashes, your open buffers stay as they were, because each buffer is its own process and none of those four owns it.

Where this promise stops

  • An extension command that hangs does block your keys. An extension's command runs inside the process that handles your keys, with no time limit. If it raises an error, Minga catches it and carries on. If it never returns, input waits. A command you declare in your own config runs as a separate task and does not block.
  • A crash of the window or terminal client ends the session. Minga treats the client going away as a quit and shuts down. Agent edits that were staged are saved on every change and come back the next time you open the project.
  • Not every crash is contained. A few shared services start before the buffers do, and a crash in one of them restarts everything started after it, buffers included. The four cases named above are the ones that leave buffers alone.

The process map, the supervision tree and the wire protocol are in the Architecture reference.

When Minga edits a file you are working in

Minga rewrites a function while you fix a line in the same file. In a tool that writes straight to disk, the last write wins and one of you loses work. Step through what Minga does instead.

  1. Minga reads the file. The read comes back with a token for exactly this text. An edit has to send that token back. If the file changed in between, Minga's whole edit is rejected and it has to read again.
  2. You approve the edit, and it is staged. Minga's copy of the file has a new line 12. The file on disk and your open buffer still have the old one.

If you edit another line

  1. You keep working. You change line 15 in your buffer. The staged edit is not in your way, and your change is not in its way.
  2. You publish. Press SPC a p and choose Publish. Minga writes its line 12 to the file and merges it into your buffer, so your buffer has both changes. Your line 15 is still yours to save.

If you edit the same line

  1. You keep working. You change line 12 in your buffer, the same line Minga's staged edit replaces.
  2. You publish, and Minga stops. Both of you changed line 12, so Minga does not overwrite yours. Your line stays in your buffer, Minga's version stays staged, and Minga opens the file's review and tells you to settle the conflict and publish again. You can also discard the staged edit.

Staged edits are not kept only in memory. Minga saves each one, with the version of the file it was made against, every time the staged set changes. The exception is a draft over the store's size limit: Minga records it as lost and tells you. If Minga crashes, the next start for the same project restores them and offers Publish and Discard again. An ordinary quit stops while anything is staged.

Where this promise stops

  • It holds in a project you open in the editor. A session that owns its staging area publishes its edits when it ends normally. That is the case when a session runs without the editor, or when the editor has no project open.
  • It covers Minga's file tools, not shell commands or Git. A shell command the agent runs is an ordinary program. By default Minga asks you before running one, and it runs in a temporary copy of the project with the staged edits applied. A command that names a path outside that copy can still write there. The copy also shares the project's deps directory and its installed node_modules packages, so a command that changes dependencies changes your project. The agent's Git stage and commit tools also ask first, and then act on your real repository.
  • A forced quit discards staged edits on purpose. :q!, :qa! and :cq quit without asking.
  • Publish waits for the agent to finish its turn. While a turn runs, Minga says so and changes nothing.

The rules for staging, merging and recovery are in Buffer-Aware Agents, and the keys are in Publishing Approved Edits.
