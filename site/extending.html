EXTENDING Config first, a package later

You want gofmt to run every time you save. That is one line of config, not a plugin project.

Minga reads one Elixir file, ~/.config/minga/config.exs. Add the line below and press SPC h r to reload it. Go files you open from then on are formatted when you save them. You write a package only when what you built has to be installed somewhere else or keep running on its own.

~/.config/minga/config.exs Elixir 
use Minga.Config

for_filetype :go, format_on_save: true

Start in one file

config.exs is ordinary Elixir. Minga reads it when it starts and again when you press SPC h r. You do not need to know the language to use it: set changes an option everywhere, for_filetype changes it for one language, and on runs your function after an event such as a save.

~/.config/minga/config.exs Elixir 
use Minga.Config

set :line_numbers, :relative

for_filetype :go,
  format_on_save: true,
  indent_with: :tabs,
  tab_width: 8

# After every save, stage the file in Git.
on :after_save, fn _buffer, path ->
  System.cmd("git", ["add", path])
end

The save hook runs in its own process, so a slow command does not hold up your typing, and a crash in it is logged while the editor keeps running. The configuration guide lists every option, and covers key bindings, your own commands, and advice, which wraps a command Minga already has.

When config is no longer enough

Config stops being enough when what you built has to leave your config file: you want to install it on another machine with one line and a version, or it needs a process of its own that keeps state while you work. Then you write a package, which Minga calls an extension. Both levels ship today.

  • Config One file, reloaded with SPC h r. Options, per-language settings, key bindings, your own commands, save hooks and advice.
  • Package A directory of Elixir files, loaded when Minga starts. It comes from a local path, a Git repository or Hex (Elixir's package registry), and runs under its own supervisor, the process that watches over it, so a crash in it does not reach the editor or another package.

One task, written both ways

Format on save is a built-in option, so it never needs a package. For a fair comparison, take something Minga has no option for: your own command on your own key. Both cards below add a command named hello_greet, bind it to the same key, and write the same line to *Messages*, Minga's message log.

Config · ~/.config/minga/config.exs Elixir 
use Minga.Config

command :hello_greet, "Say hello in *Messages*" do
  Minga.API.message("Hello from MingaHello")
end

bind :normal, "SPC o h", :hello_greet, "Say hello"
Package · ~/code/minga_hello/extension.ex Elixir 
defmodule MingaHello do
  use Minga.Extension.Editor

  command :hello_greet, "Say hello in *Messages*",
    execute: {__MODULE__, :greet}

  keybind :normal, "SPC o h", :hello_greet, "Say hello"

  @impl true
  def name, do: :minga_hello

  @impl true
  def description, do: "Says hello from a key"

  @impl true
  def version, do: "0.1.0"

  @impl true
  def init(_config), do: {:ok, %{}}

  def greet(state) do
    Minga.API.message("Hello from MingaHello")
    state
  end
end

For this task the config card is all you need. The package is the same idea with a name, a version and four short functions that identify it and run its setup. You load it with one more line of config, then restart Minga:

~/.config/minga/config.exs Elixir 
extension :minga_hello, path: "~/code/minga_hello"

Two things change when you move from the left card to the right one:

  • Where the command runs. A config command runs in its own task, outside the editor process: if it raises an error, Minga reports the error and you keep typing. A package command runs inside the editor process and receives the editor state. Minga catches a crash there and reports it, but a command that never returns blocks your input until it does, so keep slow work in the package's own process.
  • When a change takes effect. You reload config in place with SPC h r. Changed package code loads only when Minga starts again.

The package is the same file that opens the Extension API guide, which continues from here: Git and Hex sources, options your users can set, and a process of your own.

Four more places to plug in

The first two are options you set in config.exs. Model routes need a package, and grammars usually ship in one.

  • Agent hooks. A shell command that Minga runs at a point in an agent's work, such as before a tool call, where a non-zero exit stops the call. Hooks guide
  • MCP servers. External tool servers the agent can call over the Model Context Protocol (MCP); if one exits, only its tools drop out. MCP guide
  • Model routes. Send the agent's model requests to your company's gateway or to a subscription you already pay for, while Minga keeps running the tools and asking for your approval. Model routes
  • Language grammars. Add syntax highlighting for a language Minga does not ship, using a tree-sitter grammar (tree-sitter is the parser Minga highlights with) that Minga compiles and caches. Tree-sitter grammars

Task workflows: the board from the home page demo

The demo on the home page ends with a task board that Minga wrote from a spec. Minga does not ship a board. A task workflow is a view and its actions, written for one job, and it is what "quiet by default" means in practice: Minga shows nothing until something needs you, and then builds the one view your task needs.

That view comes from a definition: a short file of ordinary Elixir source that says what the view shows and what its actions do. It sits between config and a package, and you can open it and read it like any other file. The loop has five steps:

  1. Ask, or write it yourself. Ask Minga to write the definition from what your task needs, or write it yourself. Either way it uses capabilities that are already installed.
  2. Save. Saving the file attempts to activate it in the running editor. The save and the activation are reported separately, so a definition that fails to activate is still saved and still readable. Activation first needs a grant from you, and you can revoke it.
  3. Inspect. The source is in a normal buffer. Read it, change it, and save again.
  4. Keep. Keep makes the definition available in later sessions, tabs and workspaces. It does not copy the task's data, and it does not make anything start by itself.
  5. Reuse. Open the kept definition on your next spec. Minga does not have to write it again.

This page shows no definition code, because the source format is not settled yet. The design record, ADR-0004, has the details. Like config and packages, a definition is trusted code that runs with your user's permissions.

Trust, reloads and where your data goes

  • Trust. Config and packages run inside Minga, in the same Erlang VM, with your user's permissions and are not sandboxed, the same model as Emacs and Vim, so read a package before you install it. Trust model
  • Reloads. SPC h r reloads options, key bindings, hooks and advice in place; changed package code loads only when Minga restarts, and the reload tells you when a restart is needed. Why a restart (ADR-0003)
  • Where your data goes. A model route receives the conversation text and never runs a tool on your machine, and its token belongs in ~/.config/minga/credentials.json, not in config.exs. Model routes
