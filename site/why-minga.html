Thesis & Tradeoffs

Why Minga

Spawning parallel coding agents is easy now. Reviewing, steering, and shaping repeatable workflows across your editor and your agents without living inside someone else's fixed host is the harder problem.

1. Where current loops hit a wall 2. How Minga compares 3. Disposable & kept workflows 4. Zero lock-in & early gaps

1. Where the terminal multiplexer loop hits a wall

Many senior engineers have moved beyond IDE chat sidebars to CLI agents like Claude Code and Codex running inside tmux or agent multiplexers like Herdr. That workflow earned its following: persistent background daemons keep runs alive when your laptop sleeps, status sidebars show which sessions are idle or waiting on approval, and you can run vendor-native CLI harnesses side by side on flat-rate subscriptions.

The friction appears when you want editing, review, and agent execution to share one programmable environment:

  • Two disconnected worlds for editing and review. CLI agents operate on disk, so coordinating parallel edits with open editor buffers requires Git worktrees, file-watcher reloads, or per-editor bridge plugins.
  • Customization stops at the terminal edge. Multiplexers let you script tabs, status bars, hooks, and prompt files around external CLIs, but they do not own the editor buffer, diff viewer, or undo history underneath.
  • Tool churn whenever workflows evolve. Every few months a new harness ships a better review loop or task view. When workflows are baked into a closed host, adopting a better pattern means switching tools again.

What if you do not want to read every line of code?

Even if you stop reading implementation lines altogether, terminal scrollback is still a poor workbench. When your work moves up a level to specs, contracts, architecture, verification evidence, and adversarial reviews, you outgrow scrolling terminal panes faster, not slower.

The point of Minga is that the workbench reshapes itself to fit your style of work for that task, embracing disposable, customized software. Stay hands-on in the buffer when you want a native editor and staged diffs, or build a task-specific spec review view or automated check workflow when you want to work a level above the implementation. Throw it away when the task finishes, or keep it when it earns reuse across projects.

Coming from Neovim

Core Vim motions, text objects (iw, i", a{), registers, macros, marks, dot repeat, counts, language servers, and a terminal client carry over directly, and Spacebar menus are discoverable and rebindable. If your daily workflow relies heavily on a specific Neovim plugin stack (oil.nvim, fugitive, telescope, or custom Lua plugins), Minga's extension catalog is still young.

Coming from Emacs or Doom Emacs

Emacs directly inspired Minga's hooks, command advice (:before, :after, :around, :override), Spacebar leader menus, and the premise that your configuration should be written in the editor's own language. Minga runs hooks, buffers, language servers, and extensions in isolated Erlang VM processes with separate garbage-collected heaps instead of a single Lisp thread. The real tradeoff today: config options, hooks, and advice reload live, whereas compiled extension packages activate on restart to avoid split-version bugs, trading away Emacs's unrestricted live eval-defun patching of loaded packages. 3. Disposable and kept workflows (v0.1.0 direction)

Minga separates what stays fixed in the engine from what you or your agent can reshape for a task:

  • Core data stays with one owner. Open buffers own text, edits, and undo. Agent sessions own conversations, tool approvals, permissions, and crash-safe persistence (Session Recovery). Custom workflows compose those real primitives rather than scraping terminal output or inventing shadow databases.
  • Two paths to evolve the workbench. Customize Minga through readable Elixir config and extensions today (and live task-shaped definitions in v0.1.0), or extend Minga's native clients and core engine through ordinary pull requests when you need a new low-level capability.
  • Explicit boundaries for safety and recovery. Extensions and authored workflows run with OS-user privileges, so human approval gates and isolated process cleanup remain explicit rather than hidden behind magic hot-patching. See Security, privacy, and reload boundaries.

4. Zero lock-in and what is still early

Trying Minga carries zero repository lock-in. Minga never writes proprietary project files or metadata into your Git repo; your code stays an ordinary directory you can open in Neovim, Zed, or VS Code at any moment. Staged agent drafts and saved transcripts live in documented local paths under ~/.local/share/minga/, and the entire codebase is MIT open source.

Minga is pre-release software building toward v0.1.0. Current gaps to factor in before switching:

Area Current status
Live task workflows & keep-across-projects Active v0.1.0 roadmap. Config, hooks, command advice, and installable extensions ship today; live save-to-activate task surfaces and reusable shared definitions are in progress.
Staged diff review & shell overlays Diff review is currently read-only (no syntax highlighting or LSP inside the review pane; LSP checks open buffers). Shell commands inside an agent turn run on a temporary overlay copy with a separate build directory.
Inline autocomplete & debuggers (DAP) Not shipped yet. No Cursor Tab / Zed Zeta next-edit prediction or interactive DAP debugger today.
Extension ecosystem The extension runtime, custom model routes, and runtime grammar loading ship today (with early extensions such as minga-org and minga-git-extended), but the third-party catalog is tiny compared to VS Code, Neovim, or Emacs.
Platforms & binaries Signed, notarized Apple Silicon macOS app and terminal client ship via Homebrew today. Linux and Intel Macs currently require building from source; a native Linux desktop GUI is post-v0.1.0, and Windows is not supported.
