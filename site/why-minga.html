Thesis & Architecture

Why Minga

Spawning parallel CLI agents is easy now. Verifying, steering, and fixing their code without bouncing across terminal panes, worktrees, and a second editor is the real bottleneck.

1. Where the agent multiplexer loop breaks down

The most popular agent workflow right now is not an IDE at all. It is an agent multiplexer: tools like Herdr, or homegrown tmux setups, wrapping Claude Code, Codex, pi, and OpenCode in persistent terminal workspaces with status sidebars and socket APIs.

That workflow earned its adoption. Closing your laptop no longer kills an agent mid-task, one sidebar shows which sessions are working or waiting on approval, and scripts can coordinate multiple CLI agents across repositories. If your day is launching six unrelated agents across separate repos and checking on them from a status list, a PTY multiplexer fits well.

The cost shows up the moment you stay close to the code on a real, subtle change:

  • The bottleneck shifted from generating code to verifying and steering it. Terminal scrollback has no jump-to-definition, no type hover, and no live LSP diagnostics. To understand what a 400-line diff actually breaks, you flip to Neovim, Emacs, or VS Code, trace callers there, copy file paths and line numbers back into chat, and wait on another full turn for a four-line fix you could have typed yourself.
  • You get forced into slow batch handoffs instead of working on the same code together. Because CLI agents write straight to disk, editing the same file while an agent works risks clobbering unsaved buffers or scrambling undo history. Isolating every pane in its own Git worktree prevents collisions, but you pay for it with duplicated build caches, cold compiles, separate LSP indexes, and manual conflict cleanup whenever two tasks touch overlapping modules.
  • Customizing a multiplexer only changes chrome around a black box. You can script tabs, status indicators, and markdown instructions around external CLIs, but you cannot build a workflow that ties live editor state and agent turns together: staging hunks into an open buffer, rejecting one hunk while hand-editing another with undo intact, attaching live diagnostics directly to a draft, or building a custom interactive review surface you keep across projects.

Minga starts from the opposite side of that boundary: put the editor, language servers, open buffers, and agent sessions inside one programmable runtime so steering code and running agents happen in the same loop.

What if you do not want to read every line of code?

Even if you stop reading implementation lines altogether, terminal scrollback is still a poor workbench. When your work moves up a level to specs, contracts, architecture, verification evidence, and adversarial reviews, you outgrow scrolling terminal panes faster, not slower.

The point of Minga is that the workbench reshapes itself to fit your style of work for that task, embracing disposable, customized software. Stay hands-on in the buffer with native editing, LSP, and inline hunk review when you want to work close to the code, or spin up a task-specific spec review surface, architecture view, or automated check workflow when you want to work a level above the implementation. Throw it away when the task finishes, or keep it when it earns reuse across projects.

2. Neither an AI sidebar nor a PTY multiplexer

Most coding setups today choose between legacy IDEs with bolted-on chat panels or agent multiplexers wrapping terminal CLIs. Here is how those architectures compare at the runtime boundary:

Dimension AI-retrofitted IDEs Agent multiplexers & CLI harnesses (Herdr, tmux + Claude Code / Codex / pi) Minga
Runtime & persistence Single UI event loop; closing the app tears down workspace state and heavy streams contend with typing. Background server keeps PTY panes alive across disconnects; status is inferred from opaque terminal sessions. Preemptively scheduled isolated processes per buffer and session, plus minga --headless for durable local or remote runs.
How agents edit files Mutate shared editor state or patch files through an extension host bridge. Write directly to disk; concurrent work requires separate Git worktrees per pane and breaks editor undo history. Stage in isolated in-memory buffer forks for inline review (SPC a p / SPC a P), three-way merge, and real undo integration.
Code reading & auditing Full editor navigation, often weighed down by Electron chrome and extension sprawl. Diff text in terminal scrollback; you open Neovim or VS Code in another window to jump to definitions or edit. Native macOS app and terminal client with Vim and CUA editing, LSP, syntax highlighting, and inline diff review.
Orchestration & customization Fixed sidebar UX; plugin APIs wrap a host you cannot deeply reshape without forking. Socket/CLI pane spawning, scratch-file handoffs, and markdown/layout rules around external CLI processes. Config, hooks, advice, and installable extensions today, moving toward disposable or kept task workflows over real engine state.

If you live in Herdr or tmux + Neovim + CLI agents

You keep your modal muscle memory and terminal reach without splitting editing and orchestration across two worlds. Minga ships Normal, Insert, Visual, Operator-Pending, Replace, and Search modes, text objects (iw, i", a{), registers, macros, marks, dot repeat, counts, language server support, and a terminal client over the same core and headless daemon as the macOS app. CUA editing is also first-class when you want standard desktop shortcuts.

If you come from Emacs or Doom Emacs

Minga shares Emacs's core philosophy: your config is the same language as the editor, commands wrap with :before, :after, :around, and :override advice, hooks attach to lifecycle events, and SPC leader menus make deep command trees discoverable via Which-Key. What changes is the runtime underneath: hooks run concurrently instead of freezing typing, buffer-local state is isolated by process boundaries rather than global symbol tables, and there is no single-threaded wall blocking agent concurrency.

3. Programmability over real engine owners (not PTY glue)

Minga's v0.1.0 design (#3542, #3662, and our architecture decisions) draws a sharp line between what stays fixed in the engine and what you or your agent can reshape.

  • Authoritative owners stay fixed. Buffers own canonical text, edits, and undo. Agent sessions own conversations, admitted turns, tool execution, permissions, and lossless recovery (Session Recovery). Authored workflows steer and compose those authorities rather than scraping terminal output, inventing a second task database, or substituting prompt glue for real execution controls.
  • Two clear ways to evolve Minga. Customize Minga by discovering supported capabilities, authoring readable source, saving to activate, and either discarding it after the task or keeping useful definitions across projects. Develop Minga itself through normal source changes, tests, and pull requests when a task genuinely needs a new native or engine capability.
  • Explicit boundaries instead of magic hot-reloading. Today, SPC h r reloads options, keybindings, hooks, and advice cleanly in place, while compiled extension packages activate on a fresh restart so active callbacks and loaded modules never mix versions. Restricted live Save-to-activate definitions, grouped Save, and Keep are being built and verified step by step as part of v0.1.0 rather than hand-waved as unrestricted live code patching.
No hidden sandbox claims

Extensions and authored definitions run with OS-user privileges, the same trust model as Emacs Lisp and Neovim Lua. Minga uses explicit session grants and callback failure containment, not OS-level sandboxing of untrusted code. See Trust & reload boundaries.

4. Why a concurrent runtime matters

Most editors treat concurrency as an afterthought because human typing is slow compared to a CPU. Agentic work changes the load profile completely: multiple model streams, background sub-agents, shell commands, language servers, syntax reparsing, and interactive editing all happen at once.

Minga runs its core on the Erlang VM (BEAM) because four runtime properties match that workload directly:

  • Preemptive scheduling and per-process GC. Every open buffer and session has its own heap and fair CPU time. A busy agent turn or a large language-server response cannot lock out editor input or trigger a global GC pause.
  • Structural fault isolation. Buffers, agent sessions, language servers, and extensions run in separate supervised processes. A crashed tool worker or misbehaving extension callback is contained and reported cleanly without touching open buffers or unsaved edits.
  • Durable headless execution. Running minga --headless keeps agent sessions alive without a display, locally or on a remote machine, with clients attaching and detaching over the network (Remote Agents).
  • Native code where it counts. The VM never renders pixels or parses syntax trees; platform-native clients handle macOS rendering, terminal layout, and syntax parsing across clean process boundaries. See Architecture for the full diagrams and stack breakdown.

5. An honest accounting of what is still early

Minga is pre-release software building toward v0.1.0. If you are deciding whether to try it now or follow along until the release cut, here is where things actually stand:

Area Current status
v0.1.0 live authoring & Keep Active release milestone (#3542, #3662). Config, hooks, advice, and installable extensions ship today; live Save-to-activate definitions and Keep are gated on release qualification.
Extension ecosystem The extension runtime, model routes, and runtime grammar loading ship today (with early extensions such as minga-org and GitExtended), but the third-party catalog is tiny compared to MELPA, Neovim, or VS Code.
Platforms Native macOS desktop app and terminal client (macOS and Linux) ship today. A native Linux desktop GUI is post-v0.1.0.
Inline ghost text & DAP Not shipped yet. Agent work focuses on multi-file buffer-aware sessions, staged diffs, and programmable workflows.
