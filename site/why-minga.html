THESIS Design & Tradeoffs

Why Minga

Editors fail when agent chrome fights your code for screen width and focus. Terminal multiplexers escape that clutter, then strand your agents outside the editor buffer. Minga is built for engineers who want one quiet, programmable workbench shared by macOS and the terminal.

1. Why quiet chrome 2. Beyond multiplexers 3. How Minga compares 4. Disposable & reusable workflows 5. Zero lock-in & roadmap

1. Editors fail when chrome competes with your code

Most AI editors default to IDE chrome: activity rails, permanent file trees, tab bars, chat drawers, and workspace pills. You can hide those panels in VS Code, Cursor, or Zed via Zen Mode, but the surrounding workflow still assumes permanent docks and desktop-only panels. We learned the same lesson the hard way in Minga's early builds: once we added separate "Editor" and "Agent" workspaces, icon rails, and status strips, people could not tell which workspace they were in, status indicators disagreed across bars, and the macOS app and terminal client drifted apart.

Minga's interface model (ADR-0006) makes text-first the default constraint rather than an optional mode. Ordinary window splits and on-demand file switchers remain first-class, while permanent rails, tab strips, and workspace containers disappear. That is a deliberate tradeoff: if you prefer a permanent wide-screen file tree and fixed tabs on a 5K monitor, Cursor or Zed is built for that. If you want the exact same quiet muscle memory on your MacBook and over SSH in a terminal, one shared layout is the point.

2. Where the terminal multiplexer loop hits a wall

Many senior engineers moved past IDE chat sidebars to CLI agents like Claude Code and Codex inside tmux or multiplexers like Herdr. That workflow earned its following: persistent background daemons survive sleep, status panels show which sessions need approval, and you can run vendor-native CLI harnesses side by side on flat-rate subscriptions.

The ceiling shows up when you want editing, review, remote daemons, and agent execution inside one programmable environment:

  • Two disconnected worlds for editing and review. CLI agents operate on disk, so coordinating parallel edits with open editor buffers requires Git worktrees, file-watcher reloads, or per-editor bridge plugins.
  • Linear undo across two authors. When an agent edits a file you are working in, ordinary editor undo treats both authors as one timeline. Minga separates authorship so u / ⌘Z undoes only your edits while agent changes stay tracked per step and leave cleanly through Reject.
  • Customization stops at the terminal edge. Multiplexers script panes, status bars, hooks, and prompt files around external CLIs, whereas Minga lets you reshape the editor, review buffers, hooks, and agent workflows in one Elixir runtime.

What if you do not want to read every line of code?

Even when your work moves up a level to specs, contracts, architecture, verification evidence, and adversarial reviews, scrolling terminal panes gets worse, not better. Minga is built so the workbench reshapes itself to fit your task, embracing disposable, customized software: stay hands-on in the buffer when writing code, or build a task-specific spec review buffer or check workflow when supervising agents. Discard it when the work lands, or reuse it across projects.

When Herdr, tmux, or Zed is a better fit

If you want to run Anthropic's Claude Code and OpenAI's Codex CLI side by side on flat-rate vendor subscriptions, Herdr, tmux, or Zed's Agent Client Protocol is built for that. If you want a compiled Rust desktop IDE with editable multibuffer diffs and Tab prediction today, look at Zed or Cursor.

What about Cursor and VS Code?

VS Code and Cursor have massive extension ecosystems, polished inline Tab completion, and cloud agents. Minga trades Electron and fixed extension-host APIs for native macOS and terminal clients sharing one keyboard-first design over the Erlang VM.

Coming from Neovim

Core Vim motions, text objects (iw, i", a{), registers, macros, marks, dot repeat, counts, language servers, and a first-class terminal client carry over directly. Inside code buffers, y, n, =, and q stay strictly Vim. Bare single-letter review keys live only in special buffers like *minga-review* and *minga-tasks* (the same boundary fugitive and gitsigns follow). If your workflow already thrives on Neovim + gitsigns + fugitive + oil.nvim + telescope with 15ms LuaJIT startup on every Linux box, Minga's plugin catalog is still young; the reason to look at Minga is Erlang VM fault isolation, Elixir programmability, native macOS rendering with TUI parity, and integrated multi-agent review primitives without gluing a dozen Lua plugins together.

Coming from Emacs or Doom Emacs

Emacs and Doom directly inspired Minga's Spacebar leader menus (with live counts in which-key), magit-style special buffers, hooks, command advice (:before, :after, :around, :override), and writing configuration in the editor's own language. While Emacs runs I/O and LSP asynchronously via subprocesses, CPU-bound Elisp still shares one Lisp thread; Minga isolates every open buffer, hook, extension, MCP server, and agent session in its own Erlang VM process and heap. The tradeoff today: config options, hooks, and advice reload live, whereas compiled extension packages activate on restart to avoid split-version bugs (ADR-0003), trading away Emacs's live eval-defun patching of loaded packages and mature tools like magit and TRAMP. Personality stays quiet and only shows up at the edges: Minga is Bavarian for Munich ("Servus." on welcome, "Passt." once when a task finishes, and "Ciao." on quit).

Coming from VS Code, Cursor, or Zed

Minga is a Vim-first keyboard workbench by design, with an optional standard-desktop shortcut mode (set :editing_model, :cua) and first-class mouse support where every visible action has a click. Even in desktop-shortcut mode, Minga intentionally omits permanent tab strips and sidebars in favor of a fast file switcher, pinned files, and on-demand drawers. If you want standard IDE tabs, a permanent sidebar, and inline Tab prediction, Cursor or Zed will feel more immediately familiar.

4. Disposable and reusable workflows (v0.1.0 direction)

Minga separates what stays fixed in the engine from what you or your agent can reshape for a task (ADR-0004):

  • Core data stays with one owner. Open buffers own text, edits, and undo. Agent sessions own conversations, tool approvals, permissions, and crash-safe persistence (Session Recovery). Custom workflows compose those real primitives rather than scraping terminal output or inventing shadow databases.
  • Two paths to evolve the workbench. Customize Minga through readable Elixir config and extensions today (and save-to-activate task workflows in v0.1.0), or extend Minga's native clients and core engine through ordinary pull requests when you need a new low-level capability.
  • Explicit boundaries for safety and recovery. Extensions and authored workflows run with OS-user privileges, so human approval gates, revocable session grants, and automatic restoration on failed activation stay explicit rather than hidden behind silent hot-patching. See Security, privacy, and reload boundaries.

5. Zero lock-in and what comes next

Trying Minga carries zero repository lock-in. Minga never writes proprietary project files or metadata into your Git repo; your code stays an ordinary directory you can open in Neovim, Zed, or VS Code at any moment. Staged agent drafts and saved transcripts live in documented local paths under ~/.local/share/minga/, and the entire codebase is MIT open source.
