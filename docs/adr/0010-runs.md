# ADR-0010: Commands you do not type into are runs, with one record, one runner and one buffer

**Status:** Accepted (2026-11-28), with conditions on decision 6 (listed under "Conditions on decision 6") and revised the same day after four independent reviews. Design: [runs.md](../design/runs.md). Plan: the [runs workstream](https://github.com/jsmestad/minga/blob/main/docs/workstreams/runs.md). Amends [ADR-0008](0008-terminal-engine.md): Minga's commands are run blocks in `*run*`, not a separate `*minga-shell*` buffer.

## Decision

1. **A run is a command with a known command line and no keyboard input.** `:!cmd`, the test commands, the project command and every command Minga's agent runs are runs. An interactive shell is a terminal (ADR-0008), not a run.
2. **One record.** `Minga.Run` is a pure value in Layer 0: a struct with tagged states (`:needs_you`, `{:working, started_at}`, `{:done, ended_at}`, `{:failed, reason}`, `{:stopped, by}`), `started_at` and `ended_at` as plain fields beside the tag so a failed run keeps its duration, a state between a stop request and the group's exit, a separate `superseded_by` field, and transitions that pattern-match their valid source states.
3. **One owner per project.** A Layer 1 service owns runs: one `Minga.Run.Log` per project root is the only writer of records and of the `*run*` buffer. One `Minga.Run.Worker` per run owns the process, line assembly, matching, caps and timers, and reports to the Log. One event, `:run_changed`, replaces `:command_done`.
4. **One runner.** The editor's commands and the agent's shell tool share one runner: a new PTY helper that replaces both of the agent's helpers (`minga-hook-runner --shell` and `minga-shell-output-reader`) and keeps their cancel escalation and output limits. `Minga.CommandOutput` is deleted. Both `MingaEditor` and `MingaAgent` call `Minga.Run`; `Minga.Run` never references the agent. The agent keeps its job ledger, timeout policy and artifact capture, and passes them to a run as start options. The project root is a required start option, separate from the working directory, because an agent command can run in a changeset overlay directory. Agent commands are not sandboxed today and inherit Minga's environment, provider keys included: the sandbox code exists but production passes it no policy. This ADR does not change that; it fixes where a sandbox and an environment go when they are added (see "Security rules"). In short: a background job is a run, a timeout is a deadline the worker owns, and the model reads its own capture, never `*run*`. Stopping the earlier run of the same command applies only to runs you started.
5. **One PTY helper.** A native helper, `minga-run`, gives the command a PTY for stdout and stderr and `/dev/null` for stdin. The PTY is the command's controlling terminal and the command runs in a background process group, so a read from the terminal or a change to its settings stops the group; the helper reports that as "needs keyboard input". It owns the process group and stops it with signal escalation.
6. **One buffer per project.** `*run*` is buffer text through the resident-row path. Run block ranges are a value inside the buffer state (`Minga.Buffer.Blocks`), written in the same call as the text, so text and block structure never disagree in a frame. What menus, motions and frontends read is a separate, shared block description (command, cwd, author, state, exit, duration, header row, output range). A terminal block (ADR-0008, #4061) produces the same description from its own OSC 133 index; it does not use `Buffer.Blocks`, because terminal history is not buffer text.
7. **Backpressure at the worker.** The helper sends output only on demand, in frames of bounded size, and services a stop while demand is withheld. A worker keeps one demand outstanding and flushes at most about 30 times a second. `:run_changed` fires on every state transition; only progress and duration updates are rate-limited, and the modeline builder does that limiting. A run's result reaches its owner in one settle message, never through `:run_changed`.

## Owners shared with the terminal work

Issue #4061 and this ADR both claimed three things. An architecture review after Spike A recommended one owner for each, and on 2026-11-28 the owner agreed all three.

- **Agent command execution: `Minga.Run`. Agreed.** `*minga-shell*` as the agent's runner is not to be built. #4061's Option A (the tool types into one interactive shell) cannot carry background jobs beside foreground ones, several sessions at once, a fresh shell per call in the router's working directory, or a sandbox wrapped around each command. Option B is a second runner plus a mirror.
- **Approvals: `MingaAgent.Session` keeps the decision. Agreed.** A pending command is a `:needs_you` run, written only by the run log on the Session's instruction, with the run id stored on the approval. `↩` on the block opens the act menu's existing approval target (#4052). No surface writes the run record on an answer, so an answer given in one place shows everywhere. Approval still works if the run log is down; only the pending block is lost.
- **Command-block actions: one act-menu target. Agreed.** The target is `{:command_block, source}`, with a run source built in slice S2 and a terminal source added by #4061.

## Owner and failure

Added after review. Each rule is a requirement on slices S1 and S5.

- **A run has an owner process.** `Minga.Run.start` takes `owner: pid`. The worker monitors the owner and stops the run as `{:stopped, :owner_down}` when it dies, so killing an agent job still stops its command. The worker sends the owner exactly one settle message. The run is the authority for process facts; the agent's ledger records the settle and does not keep a second lifecycle.
- **Who owns your runs** *(open)*: the Editor, or the Log so an Editor restart does not end a server you started.
- **The command dies with its helper.** The helper reports the command's process group id at start and treats end-of-input on its control channel as a stop request. If the helper exits abnormally or the worker terminates, the worker kills that group directly. Spike A did not test a helper crash; S1 must.
- **Supervision.** Per project: the Log, then a supervisor of workers that are never restarted (a restart would run the command again). A Log crash ends that project's runs through the rule above, and an agent owner is told `:run_log_down`. The new Log resets the buffer's blocks.
- **The Log is not on the path of every chunk.** A stop, a start and an approval must not wait behind other runs' output, and the Editor never calls the Log synchronously. Whether workers write their own text through a block-addressed buffer operation, or send chunks to the Log and receive credit back, is chosen in S1 against this rule.
- **One source for what a block shows.** State, exit code and duration are written into `Minga.Buffer.Blocks` in the same call as the change, so a frame never shows a header without its state. The record does not also hold the range.
- **A pending approval.** The caller mints the run id and tells the Log without waiting for a reply, so approval does not depend on the Log being up. A pending run can end as denied, not admitted, or owner down; it never stays lit after its Session is gone.
- **Killing `*run*`** clears finished blocks and writes a new header for each running run. **Closing a project** stops your runs; the agent's runs follow their owner.
- **A rerun of the same command** starts when the earlier run's group has exited, not when the stop was requested.
- **Capture is a sink** the worker calls before asking for more output. A sink error ends the run as failed. Whether the sink receives raw or normalized bytes is decided at the start of S5, with the PTY-or-pipe comparison.

## Security rules

Added after review. Each is a requirement on S1 or S5.

- **Rerun never bypasses approval.** On a block Minga authored, `r`, Rerun and Rerun failed are not offered. Edit and rerun opens the Run prompt with the full command and runs only on `↩`. A pending or denied block can be started only by its approval answer.
- **You approve what runs.** The approval prompt shows the Session's full command text, unclipped, with newlines and control and bidirectional characters made visible. The answer carries the approval id, and the Session rejects an answer whose id is not its current pending approval.
- **Output is normalized before it is appended.** Colour is kept as spans; carriage returns and cursor moves are resolved within the row; every other control character, escape sequence and bidirectional override is removed. The model reads the same normalized text the block shows. A terminal block's author and state never come from in-band data.
- **Where a sandbox goes.** It wraps the command inside the helper's background group, never the helper, and must keep the run's PTY as the controlling terminal (no `bwrap --new-session`). S5 reruns the Spike A matrix under each sandbox backend before any sandbox ships.
- **Environment.** The helper starts the command with an explicit environment, not an inherited one. No run receives Minga's own provider credential variables. Agent runs do not get your login-shell environment wholesale. Workers never log output bytes.
- **One PTY per run,** closed at run end, never reused and never written by Minga.
- **Stop guarantees the process group only.** A descendant that leaves the session is a documented limit, not "stopped". On Linux the guard is a child subreaper and kills remaining descendants at run end.
- **Limits.** Runs per project and PTYs in use are capped, and a start past the cap fails visibly with the limit named.

## Conditions on decision 6

One `*run*` buffer per project holds only if all of these do. If one cannot be met inside the row-delta path, the decision becomes one buffer per run and returns to review.

1. **One fetch range and one splice per edit** ([#4397](https://github.com/jsmestad/minga/issues/4397)). Both `resident_delta_fetch_range/2` and `structural_delta_transition` in `resident_build.ex` merge a frame's edits into one bounding range today. The frame must send no rows between two distant edits and must not fall back to a full hydration. The acceptance bench adds an eviction plus an append in one frame, and a flood at the output cap.
2. **A fold change in a resident buffer is a row splice,** and re-deriving unchanged folds is a no-op. Blocks fold by themselves when a check finishes, so a fold that forces a full store replace would rebuild `*run*` on every finished check. Slice S0 inherits this as a requirement. Spike B did not measure it.
3. **`*run*` never leaves the resident path.** The store's limits are 65,536 rows and 10 MB. The Log keeps a buffer-wide budget under both by shrinking the retained tail of running runs. The per-run byte cap (8 MB) and retention counted in lines alone do not guarantee this.
4. **The output cap is cheap in steady state.** At the cap each flush drops lines after the head and appends at the end. That must not cost a pass over the whole buffer per flush.

## Context

Today `Minga.CommandOutput` runs one command per name through an Erlang Port with a pipe. It appends each chunk with a synchronous buffer call, stops a command with `Port.close` (which leaves the process group running), and has no flow control. The agent's shell tool has the right process handling and a credit-based output reader, but it is private to the agent. So the editor and the agent run commands two different ways, and only one of them can be stopped.

The design for runs needs more than either gives: coloured, line-buffered output, a visible state per run, a stop that ends the process group, errors parsed once on the BEAM, and Minga's commands shown beside yours.

## Options compared

**Keep the pipe.** Most programs block-buffer on a pipe and drop colour, so output arrives late and in bursts, and "the command asked for keyboard input" cannot be seen. It cannot meet the design.

**Wrap commands in `script` or `unbuffer`.** Flags differ by platform, `unbuffer` needs Tcl, and the PTY session escapes the group kill.

**A PTY helper with input on `/dev/null`.** Programs see a terminal for output and none for input. They colour and line-buffer their output, and they skip interactive modes that would hang. It costs a new native helper and release artifact, and tests that spawn it must be serialized.

**One buffer per run.** Simple ranges, no interleaving. It needs a second surface to switch between runs and hides Minga's commands from the place you look at your own.

## Why this one

One record and one runner mean a command behaves the same whether you or Minga started it, and stopping works everywhere. The PTY helper with no input gives real output without the detection work a full terminal needs; its code is the base for `minga-terminal` later. One buffer keeps the block grammar the terminal design already defines, and committing block ranges with the text removes a class of frames where the two disagree.

## Checks that could reverse this

- Spike A ([#4386](https://github.com/jsmestad/minga/issues/4386)): **passed.** Detection works on macOS and Linux through job-control stops, with no platform-specific scan. The check found one correction, now in decision 5: a change of terminal settings must end the run too, because `vim`, `sudo` and `ssh` change settings before they read.
- Spike B ([#4387](https://github.com/jsmestad/minga/issues/4387)): **conditional.** As the resident store is today, two runs streaming into one buffer freeze the view: edits that land in one frame are merged into a single bounding range, so a frame re-sends every row between a mid-document insert and an append (41,000 rows and 4 MB in the measurement). With one frame per edit the same workload costs 2.5 ms and 4 rows per frame at 50,000 rows, so row deltas can carry the load. The conditions are listed under "Conditions on decision 6". Frame time on the real frontends was not measured, and the spike's folded case did not use the resident path.

## Consequences

- Folded and decorated buffers must be resident before `*run*` ships (slice S0), and the per-edit range fix must land before or with S0. A folded window keeps up today only because it is not resident; making it resident first would move `*run*` onto the path that freezes.
- An append moves the buffer cursor today and a focused window follows it, and window folds do not shift when lines are inserted above them. Slice S1 must change both for run buffers: follow becomes a flag, and folds are re-derived from block ranges on every block change.
- The agent's model reads decoded PTY output, not a pipe. Spike A found `mix test` and `git diff` unchanged once colour is stripped, but `rg` and `ls` print a different format on a PTY. **Agreed 2026-11-28: agent commands use the PTY by default,** so Minga's blocks colour and stream like yours and a stuck command is visible. A pipe for stdout stays as an option of the same helper, for any class of command the model misreads; it never adds a second runner. Slice S5 starts by comparing what the model receives both ways for the agent's most common commands. The agent has its own `grep`, `find` and `list_directory` tools, so `rg` and `ls` through the shell are the minority path. The pipe option with the PTY kept as controlling terminal is untested.
- Runs set a documented environment: pagers to `cat`, plain progress for known build tools, on top of the login shell's environment.
- `:command_done` subscribers move to `:run_changed`.
- The terminal (ADR-0008) reuses the helper's PTY and process-group code and the block value. `*minga-shell*` as a separate buffer is withdrawn; nothing built it. `docs/design/terminal.md` and issue #4061 keep the commands you type in the interactive terminal.
