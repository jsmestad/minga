# Go TUI parity audit

This document is the parity gate for making the Go/Bubble Tea frontend the default terminal frontend (epic #2216, flip ticket #2222). It audits every semantic UI surface and input behavior the protocol defines, and records Go's status on each with file:line evidence.

The parity reference is the semantic protocol, not the Zig renderer. The two authorities are `docs/protocol_schema.toml` (opcode registry, wire structures, sections) and `docs/GUI_PROTOCOL.md` (semantic chrome and the `gui_action` input contract). Zig is consulted only where the spec is ambiguous. This supersedes the Go/Charm coverage row in the #2113 inventory, which reported 9/28 components before this work landed.

## Method

The audit drives outward from the schema so a missing surface cannot hide. For every semantic opcode in `protocol_schema.toml` I verified four facts about Go:

- a. BEAM emits it and Go decodes it. BEAM emitters live in `lib/minga/frontend/adapter/gui/` (31 encoders) and `lib/minga_editor/frontend/protocol/gui.ex`. Go decode is dispatched in `go/tui/internal/protocol/commands.go:152` (`DecodeCommand`) and `go/tui/internal/protocol/chrome_decode.go:9` (`decodeChrome`).
- b. Go renders it. Header and footer chrome in `render_chrome.go`, editor body and content sidebars in `render_content.go`, transient overlays in `render_surfaces.go`, floating picker in `picker_overlay.go`, which-key in `which_key_overlay.go`, agent chat in `agent_chat_panel.go`, frame composition in `frame.go`, state wiring in `model.go:179` (`applyCommands`).
- c. Input/mouse routes it. Keyboard, paste, resize, and raw mouse in `input.go`; semantic zone routing in `semantic_mouse.go`; encoders in `protocol/events.go`.
- d. Test or snapshot coverage exists. `internal/protocol/commands_test.go`, `generated_decode_test.go`, `semantic_guardrail_test.go`, `extension_runtime_test.go`, `events_test.go`, and `internal/ui/model_test.go` / `input_test.go`.

A standing guardrail test, `internal/protocol/semantic_guardrail_test.go:9`, enumerates all 41 semantic frontend opcodes and fails the build if any one lacks both a decode path and a parity classification. That test is the machine-checked backstop behind the "decode" column below.

### Validation run

`go test ./...` from `go/tui/` on this branch: 189 passed in 6 packages, suite green. The guardrail and decode tests above are part of that run.

## Status legend

- PASS: decode, render, and (where applicable) input all verified with evidence.
- GAP: missing or broken; the cell says what is missing.
- DIVERGENCE: Go behaves differently on purpose, with a one-line rationale. Non-blocking.
- N/A: surface is not meaningful in a terminal, with rationale.

## Store lifecycle and scroll reconciliation parity (shared conformance corpus)

The behavioral contract for the resident-store lifecycle and scroll-offset reconciliation is no longer maintained as prose here. It is enforced as an executable, cross-frontend test: the shared transcript corpus at `test/conformance/corpus/`, generated from the real BEAM encoder by `mix conformance.gen` (#2667). The macOS runner (`macos/Tests/MingaTests/ConformanceTranscriptTests.swift`) and the Go runner (`go/tui/internal/ui/conformance_transcript_test.go`) execute the same corpus, so any divergence in these seams fails a build.

The corpus owns the behavior claims for:

- **Store lifecycle:** 0x80 keyframe decode to a resident row set keyed by `row_id + content_hash`, 0xA2 row-delta ref resolution, ref-miss → drop → 0x80 full-recovery, 0xA0 cursor-only overlay delta, `layout_generation` full replace, and `reset_required` discard.
- **Input resolution:** drag-selection pointer normalization under an active local offset, H/M/L echo-commit (no re-anchor storm), the `scroll_seq` strictly-newer discard, the wheel-momentum-during-`ctrl-d` discard, and the same-top-jump discard (an authoritative jump landing on the previous/echoed top still bumps `scroll_seq`, #2652).

As of the Go TUI resident-store port (#2671) the corpus runs with **zero Go skips**: the Go reconciler (`internal/ui/local_presentation.go` `reconcileScroll`) now keys on `scroll_seq` ahead of the anchor-key check, mirroring Swift `shouldResetScrollPresentation`, so both `scroll_seq` transcripts pass on both frontends. Local wheel scrolling over a resident window clamps to document bounds (`internal/ui/render_content.go` `presentationScrollRowBounds`) rather than the overscan payload, so a fast fling never starves at an overscan edge; residence-off and over-threshold (windowed) buffers keep the overscan clamp byte-identically. See `test/conformance/corpus/README.md` for the fixture format and `index.json` for the authoritative transcript list.

## Gaps

### G1. Extension runtime envelope: consumed and stored, no payload-specific renderer yet (resolved, honest-minimal; #2228)

`gui_extension_runtime` (0xA3) now updates model state instead of being dropped. `applyCommands` routes `CommandExtensionRuntime` to `applyExtensionRuntime` (`model.go:302`), which stores the latest envelope per extension id in `Model.extensionRuntimes` and clears it on frame `CommandClear`. The footer surfaces the active extension ids via `extensionRuntimeStatus` (`render_chrome.go:212`) so a received envelope is observably consumed.

This is the honest-minimal close, and here is why it is not a richer UI: the payload is opaque by design. The shared protocol owns only the envelope; the named frontend extension owns the payload schema and decoder (`gui.ex:873`). The macOS side mirrors this: `gui_extension_runtime` is dispatched to a per-extension-id decoder/view in `FrontendExtensionRuntimeRegistry` (`FrontendExtensionRuntime.swift:26`), and messages for an unregistered id are a no-op. There is no in-tree `register(extensionID:)` caller on macOS, no concrete extension, and no live BEAM producer (`encode_gui_extension_runtime/3` has no caller), so there is no defined visual contract to mirror on either platform. The Go TUI therefore stores the envelope keyed by extension id (the same key Swift routes on) and exposes it for a future extension-owned terminal renderer to read. Blocking: no.

### G2. Mouse drag and multi-click (resolved; #2229)

Resolved. The verification under #2229 found the work split across two layers, and the original GAP row conflated "Go doesn't implement it" with "the system doesn't have it":

- **Multi-click (double/triple click) already worked end-to-end.** Go forwards raw presses with `click_count = 1`, and the BEAM synthesizes the 2/3 count from press timing/position (`State.Mouse.record_press/4`) and runs word/line selection (`MingaEditor.Mouse.handle_double_click`/`handle_triple_click`). Bubble Tea v2's `MouseClickMsg` exposes no native click count, so BEAM synthesis is the correct TUI path; sending `click_count = 1` is right, not a bug. Proven by `Minga.Integration.MouseTest` driving the live input router with `click_count = 1` presses.
- **Drag selection was the real Go bug.** Go reported every `MouseMotionMsg` as `MouseMotion` (0x02). The BEAM only extends a selection on `:drag` (0x03) (`input/router.ex:335`, `MingaEditor.Mouse.handle_left_drag`); free `:motion` drives hover. So buffer drag selection never fired. Fixed in `input.go` (`mousePacket` and `sgrMouseParts`): a held-button motion is now `MouseDrag` (0x03) and a free-pointer motion stays `MouseMotion` (0x02), exactly as the macOS frontend distinguishes `mouseDragged` from `mouseMoved` (`EditorNSView.swift:1219`/`:1233`).
- **Tab reorder and file-tree drop are genuinely client-side, now implemented.** `semantic_drag.go` `handleChromeDrag` tracks a press-drag-release over the existing tab and file-tree-row lipgloss zones and emits `tab_reorder` (0x48) / `file_tree_drop` (0x40). A press records a drag origin but is not consumed, so the existing tap-to-select (`select_tab` / `file_tree_click`) still fires; the reorder/drop only fires when the pointer moves onto a different valid target on release (mirroring the macOS `DragGesture` split from the tap). The drop echoes the BEAM's per-row `path_hash` (now captured into `FileTreeRow.PathHash` from the first u32 of each row), which `commands/file_tree.ex` `drop_target_matches?` re-validates against its own tree.
- **`scroll_to_line` (0x2F) is skip-not-rendered.** The Go TUI draws no scroll indicator/scrollbar, so there is no surface to drag; vertical scroll stays wheel/keyboard driven. This is a DIVERGENCE row, not a gap.

Blocking: no (was non-blocking; now PASS for the rendered surfaces).

### G6. Mouse click routing covers the directly-rendered secondary chrome; the rest is bounded by render shape (non-blocking, narrowed by #2230)

Routed under #2230 with lipgloss zones and `gui_action` encoders (`semantic_mouse.go`, `events.go`): breadcrumb segments (`breadcrumb_click`), completion rows (`completion_select`), sidebars (`sidebar_action`, sending `activate` for an inactive sidebar and `toggle` for the active one, mirroring `ActivityBar.swift:39`), and the hover popup action (`hover_open_action`). These were the surfaces the Go TUI renders directly into the linear header/body/footer flow that `m.zones.Scan` walks (`model.go:187`), so a per-element zone marker survives to mouse time. Completion was converted from an opaque charm list to direct addressable rows to make this possible without changing its look (`render_chrome.go renderCompletion`).

The remaining G6 surfaces are not routed, for concrete structural reasons rather than oversight:

- Rendered through charm `list`/`table` components that emit one opaque multi-line block with no per-row addressability (`components.go`): agent context. Marking a per-row zone would require replacing the renderer wholesale, which is out of scope for a click-routing ticket (do not build new rendering surfaces). Notifications was routed under #2333, and observatory + edit-timeline under #2334/#2335, by converting their renderers to addressable rows (the same conversion completion got under #2230), so they are no longer in this bucket.
- Composited as a floating `lipgloss.Layer` in `composeFrame` (`frame.go:17`), which runs after `m.zones.Scan` and re-renders into a cell buffer that drops the custom zone escape markers: picker rows. Routing these needs the scan moved to post-composite and the compositor made marker-aware, an architecture change beyond this ticket.
- The clickable sub-element is not rendered in the Go TUI at all, so there is nothing to attach a zone to: git status files (Go shows a compact git summary, not an interactive status panel; see the Git status row DIVERGENCE) and the bottom-panel tab bar (only the active tab title renders, so panel_switch_tab/dismiss/resize have no target). Building those panels is a rendering ticket, not a routing one. (Notifications previously sat here because only title/body rendered; #2333 added the dismiss glyph and inline-action affordances and routed them, so it moved to PASS.)
- Gutter fold markers render per-row but only inside composed window-content lines via `composeSemanticLine` width math (`render_content.go`); attaching a stable zone to a single fold glyph there is entangled with window placement and was deferred.

Each unrouted surface is still keyboard-reachable, which Go forwards as `key_press`, so the terminal stays fully operable; what is missing is point-and-click convenience on the chrome that Go does not render directly. Blocking: no.

There are no GAP rows that block the flip. Every blocking-tier surface (window content and deltas, gutter, theme, tabs, status/modeline, picker, completion, which-key, file tree, agent chat, split separators, indent guides, keyboard, paste, resize, clipboard write, core mouse) is PASS.
